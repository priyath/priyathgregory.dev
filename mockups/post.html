Architect a Production-Grade GKE Environment

Node pools, VPC-native networking, workload identity, and autoscaling — what it actually takes to run Kubernetes in production on Google Cloud.

PG
Priyath Gregory
Mar 2023 · 12 min read
gke kubernetes architecture

Building a production-ready Kubernetes cluster on Google Kubernetes Engine involves far more than running gcloud container clusters create. This post walks through the architectural decisions, configuration choices, and operational concerns that separate a toy cluster from one you'd trust with real traffic.

Why GKE Over Self-Managed Kubernetes?

The control plane is a significant operational burden — etcd management, API server upgrades, certificate rotation. GKE handles all of this, letting you focus on the workload layer. But "managed" doesn't mean "hands-off" — you still own node configuration, networking, autoscaling, and security posture.

The hardest part of Kubernetes is not the initial setup — it's the operational discipline required to keep a cluster healthy at scale over time.

Node Pool Strategy

A production cluster should separate workloads by node pool. A common pattern is three pools: one for system components (with a NoSchedule taint), one for general application workloads, and optionally a third for GPU or high-memory workloads.

node-pools.tf
terraform 
resource "google_container_node_pool" "system" {
  name       = "system-pool"
  cluster    = google_container_cluster.primary.id
  node_count = 2

  node_config {
    machine_type = "e2-standard-4"
    taint {
      key    = "node-role"
      value  = "system"
      effect = "NO_SCHEDULE"
    }
  }
}

VPC-Native Networking

Always use VPC-native clusters (alias IP ranges) over routes-based clusters. Pod IPs are directly routable within your VPC, you get better Cloud Load Balancing integration, and a smaller blast radius for IP exhaustion. The key: specify secondary IP ranges at creation time — they cannot be changed without recreating the cluster.

Workload Identity

Never use node-level service account keys. Workload Identity binds a Kubernetes service account to a Google service account via OIDC federation — each workload gets scoped GCP credentials without key files in your containers or Secrets.

workload-identity.tf
terraform 
# Bind the k8s service account to a GCP service account
resource "google_service_account_iam_member" "workload_identity" {
  service_account_id = google_service_account.app.name
  role               = "roles/iam.workloadIdentityUser"
  member = "serviceAccount:${var.project}.svc.id.goog[${var.namespace}/${var.ksa_name}]"
}
